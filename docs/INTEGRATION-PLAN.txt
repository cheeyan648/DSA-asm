PART 1 - WHERE WE ARE NOW (AS-IS)
================================================================================

Four modules, four islands. Each control class owns its own data and none of
them read each other's.

  MODULE 1  Walk-In Registration    WalkInGuest        walkInGuests.dat      OK
  MODULE 2  Housekeeping Task Log   HousekeepingTask   housekeepingTasks.dat OK
  MODULE 3  Front-Desk Service      FrontDeskRecord    bookings.dat          OK
            (wraps Booking + BillingRecord)
  MODULE 4  Loyalty & Rewards       Member, Reward,    *** NO .dat FILE ***
                                    Redemption,
                                    LoyaltyNotification

THE FOUR PROBLEMS TO SOLVE

  P1. Loyalty has NO persistence at all.
      LoyaltyRewardsMaintenance only calls RewardInitializer for the reward
      catalogue. memberList, redemptionHistory and notificationList are plain
      in-memory ArrayLists. Every member registered is LOST when you quit.
      There is no MemberDAO, no RedemptionDAO, no members.dat.

  P2. "Room" exists only as a loose String, duplicated in three modules.
      Booking.roomNumber and HousekeepingTask.roomNumber are both String
      "1001". Nothing guarantees they refer to the same room, nothing lists
      what rooms exist, and nobody knows a room's type or price. Room is a
      real entity that has never been written.

  P3. Booking.memberId is a dead field.
      The field exists and is documented as the link to Loyalty, but grep
      shows ZERO writes to it outside the entity itself. BookingInitializer
      never sets it. So the Front-Desk <-> Loyalty bridge is declared but
      never built.

  P4. A walk-in guest never becomes a booking.
      Module 1 serves a guest off the queue and the trail stops dead. No
      Booking is created, no room assigned, no housekeeping triggered.
      WalkInGuest.guestId and Booking.confirmationNumber are unrelated.

CAN WE REUSE THE EXISTING .dat AND Initializer CLASSES?

  YES - reuse the PATTERN, but the FILES must be regenerated once.

  Reuse as-is (no change needed):
    - adt.ArrayList / ArrayQueue / ArrayStack / BookingBST - all fine
    - The DAO shape itself (ObjectOutputStream loop) - proven, keep it
    - The "load, if empty then initialize and save" bootstrap in every
      control constructor - keep this exact pattern for the new DAOs
    - RewardInitializer - reusable unchanged, catalogue is standalone
    - HousekeepingTaskInitializer - reusable, only needs roomId values to
      match the new Room table (it already uses 1001-1010, which is fine)

  Must be regenerated (NOT backward compatible):
    - bookings.dat        - Booking gains roomId + memberId actually populated
    - walkInGuests.dat    - WalkInGuest gains convertedBookingNo + assignedRoom
    - housekeepingTasks.dat - HousekeepingTask gains sourceBookingNo, staffId

  WHY THEY MUST BE REGENERATED
  Java serialization matches on serialVersionUID. Adding fields to a class
  whose old .dat was written under a different UID throws
  InvalidClassException on load. Two entities are already exposed here:
  Booking, HousekeepingTask, Member, Redemption, Reward and
  LoyaltyNotification do NOT declare serialVersionUID at all, so the JVM
  computes it from the field list - meaning ANY field you add silently
  breaks the old file.

  ACTION: add  private static final long serialVersionUID = 2L;  to EVERY
  entity, then delete the three .dat files once. The initializers rebuild
  them on next run. After that the UID is pinned and future changes are safe.
  This is a one-time cost and it is worth paying now.

PART 4 - CROSS-MODULE PROCESS FLOW
================================================================================

FLOW A : WALK-IN GUEST BECOMES A PAYING, POINT-EARNING STAY
This is the flow that proves all four modules are integrated.

  [M1] 1. Guest walks in -> register -> WalkInGuest(WAITING) queued
          If they give a memberId, link GUEST.memberId now.

  [M1] 2. Officer serves next in queue (urgent first, else FIFO)
          -> WalkInGuest.status = SERVED

  [M2] 3. System asks Module 2 for a room where
          cleanStatus = "Ready for Check-In" AND occupancyStatus = VACANT
          -> returns roomId 1003          <<< M1 READS M2

  [M3] 4. Module 3 creates BOOKING
             guestId, roomId=1003, memberId (if any),
             bookingSource = WALK_IN, status = CHECKED_IN
          creates BILLINGRECORD priced at ROOM.ratePerNight x nights
          -> WalkInGuest.convertedBookingNo = new confirmationNo
                                          <<< M1 WRITES M3
  [M2] 5. ROOM.occupancyStatus = OCCUPIED  <<< M3 WRITES M2

  [M3] 6. Guest checks out, settles bill -> status = CHECKED_OUT

  [M2] 7. AUTO-CREATE HousekeepingTask(roomId=1003, "Dirty",
             sourceBookingNo = that booking)
          ROOM.occupancyStatus = VACANT    <<< M3 TRIGGERS M2

  [M4] 8. IF booking.memberId != NULL:
             points = floor(BillingRecord.totalBill / 10)
             MEMBER.points += points
             MEMBER.totalStays++
             MEMBER.lifetimeSpend += totalBill
             re-evaluate tier against thresholds (1000/5000/10000)
             IF tier changed -> LoyaltyNotification(TIER_UPGRADE)
                                          <<< M3 WRITES M4

  [M2] 9. Housekeeper cleans: Dirty -> Cleaning -> Inspected -> Ready
          ROOM.cleanStatus mirrors the latest task
          Room is now available for step 3 again. LOOP CLOSED.

FLOW B : LOYALTY DISCOUNT APPLIED AT THE COUNTER

  [M4] 1. Member requests redemption -> Redemption(PENDING) enqueued
  [M4] 2. Manager processes -> COMPLETED, MEMBER.points -= pointsUsed
  [M3] 3. At checkout the reward is applied to BILLINGRECORD as a discount
                                          <<< M4 WRITES M3
  [M4] 4. LoyaltyNotification(REDEMPTION) raised

FLOW C : HOUSEKEEPING BLOCKS A BOOKING

  [M3] 1. Front desk attempts to assign room 1005
  [M2] 2. Module 2 reports cleanStatus = "Dirty"
  [M3] 3. Assignment REFUSED, alternative Ready room offered
                                          <<< M3 READS M2

MODULE DEPENDENCY MATRIX   (row reads/writes column)

              | M1 WalkIn | M2 House | M3 Front | M4 Loyalty
  ------------+-----------+----------+----------+-----------
  M1 WalkIn   |    -      |  READ    |  WRITE   |  READ
  M2 House    |    -      |    -     |  READ    |    -
  M3 Front    |  WRITE    |  WRITE   |    -     |  WRITE
  M4 Loyalty  |    -      |    -     |  READ    |    -

MODULE 1 - WALK-IN REGISTRATION & STANDARD BOOKING       (Wong Chee Yan)
--------------------------------------------------------------------------------
PURPOSE
  Manages guests who arrive with NO reservation. It is the front door of the
  system: it decides WHO gets served and IN WHAT ORDER, fairly and auditably.

CORE PROBLEM IT SOLVES
  Pure first-come-first-served is unfair to an elderly guest, a guest with a
  medical need, or one travelling with an infant. But letting staff jump the
  queue freely invites abuse. M1's answer: allow the exception, but FORCE a
  written reason and audit every one of them.

WHAT IT ACTUALLY DOES (from the menus)
  1. Guest registration
       - Register normal walk-in       -> joins BACK of queue
       - Register urgent walk-in       -> exception case, reason MANDATORY
       - Undo last registration        -> Stack pop, for mis-keyed entries
  2. Queue operations
       - Serve next guest              -> urgent first, then earliest arrival
       - Display current queue         -> paged, shows position + who's ahead
       - Cancel a waiting guest
  3. Search & filter    by guest ID / partial name / status / guest type
  4. Sorted listings    by arrival / name A-Z / longest waiting / service order
  5. Reports
       - Queue Performance Analysis    -> avg wait, served vs cancelled
       - Urgency Exception Audit       -> every override + its stated reason

DATA IT OWNS      WalkInGuest -> walkInGuests.dat
ADT               ArrayList (records) + service-order logic (queue discipline)
                  + ArrayStack (undo last registration)
STATUS LIFECYCLE  WAITING -> SERVED  or  WAITING -> CANCELLED

INTEGRATION ROLE (what changes)
  TODAY  a guest is marked SERVED and the trail STOPS DEAD. Nothing follows.
  AFTER  serving triggers: ask M2 for a clean vacant room -> ask M3 to create
         the Booking -> write convertedBookingNo back onto the WalkInGuest.
         M1 becomes the ENTRY POINT of the whole system instead of a dead end.


--------------------------------------------------------------------------------
MODULE 2 - HOUSEKEEPING TASK LOG                          (Gan Zhi Ying)
--------------------------------------------------------------------------------
PURPOSE
  Tracks the cleaning state of every room. It is the GATEKEEPER of room
  readiness - the only module entitled to say "this room may be sold".

CORE PROBLEM IT SOLVES
  A room must never be given to a guest while dirty, and a status logged by
  mistake must be reversible without corrupting history. Hence the rollback
  stack (LIFO: only the MOST RECENT update can be undone).

WHAT IT ACTUALLY DOES (from the menus)
  1. Log new task status update     -> new timestamped entry, duplicate-blocked
  2. Rollback last status update    -> Stack pop, confirmation required
  3. Display task log               -> chronological history
  4. Search Housekeeping Task
  5. Reports

STATUS PIPELINE (strict forward order)
  Dirty -> Cleaning In Progress -> Inspected -> Ready for Check-In
  ONLY "Ready for Check-In" means the room is sellable.

DATA IT OWNS      HousekeepingTask -> housekeepingTasks.dat
ADT               ArrayList (log) + ArrayStack (rollback history)
KEY DESIGN NOTE   It is an append-only LOG, not a room table. Current state of
                  a room = its LATEST entry. This is why entity Room is needed:
                  there is nowhere today to store a room's type or rate.

INTEGRATION ROLE (what changes)
  TODAY  logs statuses against a loose String roomNumber nobody validates.
  AFTER  roomId becomes a real FK to ROOM; a M3 check-out AUTO-CREATES a
         "Dirty" task carrying sourceBookingNo; and M2 answers the query
         findReadyVacantRoom() that M1 and M3 depend on to assign any room.
         M2 gains the power to REFUSE a booking (Flow C).


--------------------------------------------------------------------------------
MODULE 3 - FRONT-DESK SERVICE                             (Tew Yong Le)
--------------------------------------------------------------------------------
PURPOSE
  Creates and manages BOOKINGS and their BILLS. This is the commercial heart
  and the SPINE of the integrated ERD - every other module links to Booking.

CORE PROBLEM IT SOLVES
  Bookings must be found fast by confirmation number and listed in sorted
  order, and no two guests may occupy one room on overlapping dates.

WHAT IT ACTUALLY DOES (from the menus)
  1. Create new booking          -> guest + room + dates + bill
  2. Search information
       - Search guest information
       - Search billing details
  3. Check room availability     -> date-overlap detection
  4. Display all bookings        -> BST in-order traversal = auto-sorted
  5. Reports

DATA IT OWNS      Booking + BillingRecord, wrapped as FrontDeskRecord
                  -> bookings.dat
ADT               BookingBST (Binary Search Tree, keyed on confirmationNumber)
                  + ArrayList. BST gives O(log n) lookup and free sorted output.
BILLING           totalBill, amountPaid; outstandingBalance and paymentStatus
                  (PAID / OUTSTANDING) are DERIVED, not stored.

INTEGRATION ROLE (what changes)
  TODAY  most isolated of all: roomNumber is a String M2 never sees, and
         memberId EXISTS on Booking but is NEVER WRITTEN (dead field).
  AFTER  M3 becomes the hub that WRITES to all three other modules:
           -> M2  check-out auto-creates the Dirty housekeeping task
           -> M4  check-out awards points and updates tier
           -> M1  receives convertedBookingNo when a walk-in converts
         Booking gains guestId, bookingStatus, bookingSource; roomNumber
         becomes a real FK roomId priced from ROOM.ratePerNight.

MODULE 4 - LOYALTY & REWARDS                              (Ivan Tan Yann Rong)
--------------------------------------------------------------------------------
PURPOSE
  Retains guests. Tracks points, tiers, reward redemptions and notifications.

CORE PROBLEM IT SOLVES
  Redemption requests must be handled FAIRLY IN ORDER (hence the queue), and
  points must never be deducted for a request that is later rejected.

WHAT IT ACTUALLY DOES (13 menu options - the largest module)
  MEMBERS      1 Register new member
               2 Search member by ID
               3 Display all members
               4 Display members sorted by points
               5 Find members with expiring points
               6 Accumulate member points
  REWARDS      7 View rewards
               8 Request reward redemption      -> enqueued as PENDING
               9 Process next pending redemption -> FIFO dequeue
              10 View redemption history
  ENGAGEMENT  11 View member notifications
              12 View personalized promotion
  REPORTS     13 Loyalty Membership & Tier Performance / Redemption Analysis

TIER THRESHOLDS   Silver -> Gold 1000 -> Platinum 5000 -> Diamond 10000 pts
REDEMPTION RULE   Points are deducted ONLY when a PENDING redemption is
                  COMPLETED. REJECTED redemptions never reduce points.
                  (Explicitly documented in LoyaltyRewardsMaintenance.)
STATUSES          PENDING -> COMPLETED  or  PENDING -> REJECTED

DATA IT OWNS      Member, Reward, Redemption, LoyaltyNotification
ADT               ArrayList x4 + ArrayQueue (pending redemptions, FIFO)

*** ITS CRITICAL DEFECT ***
  NO PERSISTENCE. Only RewardInitializer is called; memberList,
  redemptionHistory and notificationList are plain in-memory ArrayLists.
  There is no MemberDAO and no members.dat. EVERY MEMBER REGISTERED IS LOST
  ON EXIT. This is why Phase 2 is scheduled first after safety.

INTEGRATION ROLE (what changes)
  TODAY  fully self-contained; points are added by hand via option 6.
  AFTER  points are earned AUTOMATICALLY from a real stay: M3 check-out calls
         awardPointsForStay() -> points, totalStays, lifetimeSpend update,
         tier re-evaluated, TIER_UPGRADE notification raised. Redemptions
         become real money off a real bill (Flow B). Option 6 stays as the
         manual override.

   ARRIVES        WAITS         GETS ROOM      PAYS         EARNS       LEAVES

   [  M1  ]---->[  M1  ]------>[  M2  ]---->[  M3  ]---->[  M4  ]---->[  M2  ]

================================================================================
APPENDIX B - M1 WALK-IN REGISTRATION  vs  M3 FRONT-DESK SERVICE
Why they are NOT the same thing, and where the line sits.
================================================================================

THE CONFUSION
  Both modules deal with "a guest getting a room", so they sound duplicated.
  They are not. They handle two DIFFERENT HALVES of the counter, separated by
  one clean line:

      M1 manages the PERSON standing in front of the counter.
      M3 manages the CONTRACT that person signs.

  M1 = "Whose turn is it?"          -> a QUEUE problem (people, time, fairness)
  M3 = "What did they buy?"         -> a RECORD problem (dates, room, money)

  A guest can be in M1 and never reach M3 (they give up and leave -> CANCELLED).
  A booking can exist in M3 that never touched M1 (phone or online reservation).
  The two only meet at ONE moment: when a served walk-in becomes a booking.


--------------------------------------------------------------------------------
SIDE-BY-SIDE
--------------------------------------------------------------------------------

                        M1 WALK-IN REGISTRATION    M3 FRONT-DESK SERVICE
  --------------------- -------------------------- -------------------------
  Question answered     "Who is served next?"      "What was booked?"
  Subject               A PERSON waiting           A CONTRACT/STAY
  Entity                WalkInGuest                Booking + BillingRecord
  Primary key           WG1001 (walkInId)          10000001 (confirmationNo)
  Time model            NOW - live, minute by      FUTURE/PAST - date ranges
                        minute (arrivalTime,       (checkInDate ->
                        servedTime, waiting mins)  checkOutDate)
  Lifespan of a record  MINUTES to hours           DAYS to months
  Core ADT              Queue discipline + Stack   Binary Search Tree
                        (undo)                     (keyed confirmationNo)
  Why that ADT          Order of arrival matters;  Fast O(log n) lookup by
                        fairness is the whole      key + free sorted output
                        point                      via in-order traversal
  Does it know a ROOM?  NO - not one room field    YES - roomNumber is central
  Does it know MONEY?   NO - no price anywhere     YES - totalBill, amountPaid
  Does it know DATES?   NO - only timestamps       YES - it IS date ranges
  Guest may not exist?  They are physically there  Booking may be for someone
                                                   arriving next month
  Reservation?          NO - "no prior booking"    YES - that is the record
  Statuses              WAITING / SERVED /         (booking has no status
                        CANCELLED                  field today - to be added)
  Fairness logic        YES - urgent-first with    NONE - no ordering concern
                        mandatory audited reason
  Conflict logic        NONE                       YES - date-overlap check
                                                   (isRoomAvailable, line 522)


--------------------------------------------------------------------------------
PROOF FROM THE CODE - THE CLEANEST EVIDENCE
--------------------------------------------------------------------------------

  entity/WalkInGuest.java has NO room, NO date, NO price:
      guestId, name, contactNumber, urgent, urgencyReason,
      arrivalTime, servedTime, status
                    ^^^ nothing about WHAT they are buying

  entity/Booking.java has NO queue concept:
      confirmationNumber, guestName, roomNumber,
      checkInDate, checkOutDate, memberId
                    ^^^ nothing about WHEN they arrived or WHO waited longer

  The two entities share ZERO fields except a human name. That is the proof
  they are genuinely different concerns, not duplicates.

  M1 serveNextGuest()  (line 315)     -- what "serving" means today
      next.setStatus(STATUS_SERVED);
      next.setServedTime(LocalDateTime.now());
      saveToFile(...);
      -> flips a flag and stamps a time. NO room assigned. NO booking made.
         NO bill. THE TRAIL ENDS HERE. This is the integration gap.

  M3 createBooking()   (line 199)     -- what "booking" means today
      inputBooking() -> validate 4-digit room -> reject duplicate
      confirmation -> isRoomAvailable(room, in, out) -> input totalBill
      -> input amountPaid -> store FrontDeskRecord
      -> starts from a BLANK FORM. It never asks "who is next in the queue?"
         It has no idea M1 exists.


--------------------------------------------------------------------------------
THE ANALOGY
--------------------------------------------------------------------------------
  Think of a clinic:

      M1 = the WAITING ROOM and the number ticket machine
           Cares about: who arrived first, who is an emergency, how long
           people have waited. Cares nothing about the diagnosis.

      M3 = the CONSULTATION ROOM and the invoice
           Cares about: what treatment, which room, how many nights, how much
           to pay. Cares nothing about who was waiting outside.

  You need BOTH. A clinic with only a waiting room never treats anyone;
  a clinic with only a consultation room descends into a shouting match at
  the door.


--------------------------------------------------------------------------------
THE OVERLAP THAT LOOKS LIKE DUPLICATION (and why it is not)
--------------------------------------------------------------------------------
  Three things appear in both, but mean different things:

  1. A NAME
       M1 name          = who is standing here right now
       M3 guestName     = whose name the reservation is under
       These can differ: a secretary books for a director.
       FIX: both become FK guestId -> GUEST. One identity, two roles.

  2. "AVAILABILITY"
       M1 has none. It never asks whether a room is free.
       M3 isRoomAvailable() = is this room free FOR THESE DATES (no overlap)
       M2 cleanStatus       = is this room PHYSICALLY CLEAN right now
       Three different questions. Today only M3's exists, and it is blind to
       whether the room is dirty - a real defect (Flow C fixes it).

  3. "SERVED" vs "CHECKED_IN"
       M1 SERVED     = the officer finished TALKING to this person
       M3 CHECKED_IN = the guest has legally taken occupancy of a room
       Today M1's SERVED leads to nothing, so the difference is invisible.
       After integration SERVED triggers the creation of a CHECKED_IN booking.


--------------------------------------------------------------------------------
WHERE THEY MEET - THE HANDOVER (the single integration point)
--------------------------------------------------------------------------------

   M1 TERRITORY                    |  M3 TERRITORY
   the person                      |  the contract
   ------------------------------- + ---------------------------------------
   Guest walks in, no reservation  |
   Register -> WG1007, WAITING     |
   Queue: urgent first, else FIFO  |
   Officer picks "Serve next"      |
   Status -> SERVED, servedTime    |
                                   |
        >>>>>>>>>>>> HANDOVER LINE <<<<<<<<<<<<
        M1 asks M2: findReadyVacantRoom() -> 1003
        M1 asks M3: convertWalkInToBooking(WG1007, 1003)
                                   |
                                   |  Booking 10000042 created
                                   |    guestId, roomId=1003,
                                   |    bookingSource = WALK_IN
                                   |    bookingStatus = CHECKED_IN
                                   |  BillingRecord priced from
                                   |    ROOM.ratePerNight x nights
                                   |
   WalkInGuest.convertedBookingNo  |  <- written back so the queue record
     = "10000042"                  |     points at its own outcome
   ------------------------------- + ---------------------------------------

  ONE FIELD carries the whole handover: WalkInGuest.convertedBookingNo.
  That single FK is what turns two isolated modules into one system.

  Note bookingSource: after integration M3 will hold BOTH kinds of booking -
    bookingSource = WALK_IN  -> came through M1's queue
    bookingSource = ONLINE / PHONE -> never touched M1 at all
  This proves M3 is the SUPERSET. M1 is one of several doors into it.


--------------------------------------------------------------------------------
ONE-LINE ANSWER (for the presentation / viva)
--------------------------------------------------------------------------------
  "Module 1 manages the QUEUE OF PEOPLE waiting at the counter - it answers
   'whose turn is it, and is that fair?' using arrival times and audited
   urgency overrides. Module 3 manages the BOOKING RECORD AND THE BILL - it
   answers 'which room, which dates, how much?' using a BST for fast lookup
   and date-overlap checks for conflicts. Module 1 has no room, no date and
   no price; Module 3 has no queue and no waiting time. They meet at exactly
   one point: when a served walk-in is converted into a booking, recorded by
   WalkInGuest.convertedBookingNo."

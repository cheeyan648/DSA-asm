1. THE 60-SECOND OPENING
--------------------------------------------------------------------------------

"This module is the front desk counter. Agents handle a constant stream of
inquiries - room availability, billing questions, and guest identification by
an 8-digit confirmation number. The spec asks for instant retrieval, so lookup
speed is the design driver for this whole module.

That is why I built a Binary Search Tree. Every booking is keyed on its
confirmation number, so a lookup is O(log n) instead of scanning every booking.
With a thousand bookings that is about ten comparisons instead of a thousand.

I store each booking in two places on purpose: the BST for fast lookup, and the
team's List ADT for traversal and reporting. Different access patterns, so
different structures."

3. ADT WALKTHROUGH - BINARY SEARCH TREE
--------------------------------------------------------------------------------

DECLARATION                             line 53
    private final BookingBST bookingTree = new BookingBST();

STRUCTURE                               BookingBST.java line 17
    private class Node {
        private Booking data;
        private Node left;
        private Node right;
    }

  Each node holds one Booking. Left subtree holds SMALLER confirmation numbers,
  right subtree holds LARGER. That invariant is what makes search work.


STEP 1 - INSERT                         BookingBST.add(), line 34

    Node current = root;
    while (true) {
        int comparison = booking.getConfirmationNumber()
                            .compareTo(current.data.getConfirmationNumber());
        if (comparison == 0)  return false;        // duplicate - reject
        else if (comparison < 0) { ...go left...  }
        else                     { ...go right... }
    }

  Walks down from the root, comparing, until it finds an empty child slot.

  Inserting 50231847, then 20114563, then 78905512:

                    [50231847]
                   /          \
           [20114563]        [78905512]

  *** THE DUPLICATE CHECK IS FREE - SAY THIS ***
  "I do not need a separate pass to check for duplicates. Finding where to
  insert and checking whether it already exists are the same walk down the
  tree. comparison == 0 means I have landed on it. A List would need a full
  O(n) contains() scan before every insert; the tree gets it for nothing."

  This is the single best thing to lead with. It shows you understand WHY the
  structure was chosen, not just that you used it.

  Complexity: O(log n) average, O(n) worst case.


STEP 2 - SEARCH                         searchBookingByConfirmationNumber(),
                                        line 300
    return bookingTree.search(confirmationNumber);

  Same walk. Compare, go left or right, until found or you fall off the tree.

  WORKED EXAMPLE - have this ready on paper:
      Looking for 78905512 in the tree above.
      Compare with root 50231847 -> larger -> go right.
      Compare with 78905512      -> equal  -> found.
      Two comparisons.

  THE NUMBER TO QUOTE: "With 1000 bookings, about 10 comparisons instead of up
  to 1000. log base 2 of 1000 is roughly 10."


STEP 3 - IN-ORDER TRAVERSAL             getAllBookings()

  Visit left subtree, then the node, then right subtree. That order yields the
  bookings in ASCENDING confirmation-number order.

  SAY THIS: "Menu 5 shows bookings sorted, and I never call a sort. The tree's
  structure already encodes the order - the traversal just reads it out. That
  is a second benefit of the BST I get for free alongside the fast lookup."

  Complexity: O(n) - every node visited exactly once.

  Returns a ListInterface<Booking>, so the tree hands its contents back in the
  TEAM ADT. Worth pointing out: the two structures interoperate.

4. ADT WALKTHROUGH - LIST (THE TEAM ADT)
--------------------------------------------------------------------------------

DECLARATIONS                            lines 36, 62, 68
    private final ListInterface<FrontDeskRecord> recordList = new ArrayList<>();
    private final ListInterface<Booking>     bookingList    = new ArrayList<>();
    private final ListInterface<BillingRecord> billingList  = new ArrayList<>();

  All declared by INTERFACE, not by ArrayList. Spec §4.5.4 asks about exactly
  this. Answer: it restricts callers to the interface methods, and lets the
  implementation be swapped without changing any other line.


WHY BOTH A TREE AND A LIST              line 90 comment, line 167 comment

  Every booking goes into BOTH:
      bookingTree.add(booking);      lookup by key       O(log n)
      bookingList.add(booking);      traversal, reports  O(1) append

  SAY THIS: "The tree answers 'find this one booking'. The List answers 'walk
  every booking'. Reports need the second, and a tree traversal for every
  report would be clumsier than just keeping a list. I trade a little memory
  for the right structure for each job."

  LIKELY FOLLOW-UP: "Isn't storing it twice wasteful?"
  ANSWER: "Both hold REFERENCES to the same Booking objects, not copies. The
  extra cost is one pointer per booking, not a second copy of the data."
  Know this - it is the difference between a good answer and a shaky one.


SELECTION SORT                          sortBookingByCheckInDate(), line 735

  Used by the booking summary report to order by check-in date ascending.

  How it works: find the minimum in the unsorted portion, swap it into place,
  repeat for the next position.

  COMPLEXITY - know these:
      Best / average / worst   O(n squared) ALWAYS - no early exit possible,
                               it must scan the remaining portion every pass
      Swaps                    O(n) - fewest swaps of the simple sorts
      Space                    O(1) - in place

  IF ASKED "why selection sort?"
  "Report lists are small. Selection sort does the fewest swaps of the simple
  sorts, which matters if swapping is expensive. But I should be honest - merge
  sort in the team ADT is O(n log n) and would be the better choice if the data
  grew. For a report of a few dozen bookings the difference is invisible."

  IF ASKED "is it stable?"
  "The classic implementation is NOT stable - swapping a distant minimum into
  place can jump an equal element over another. Merge sort in our team ADT IS
  stable. If ties needed to keep their original order I would use that instead."

  Do not guess on this one. Selection sort's instability is a standard exam
  question.

"Add a method to count the tree's nodes."
    getNumberOfEntries() already exists - it is maintained as a counter on
    insert, so it is O(1) rather than a traversal. Say that.

"Write a method to find the smallest confirmation number."
    Walk left from the root until left is null. O(log n).
        Node current = root;
        while (current.left != null) current = current.left;
        return current.data;
  A classic BST question. Practise it - the mirror (largest = walk right) too.

"How would you delete a node?"
    You have NOT implemented delete. Say so, then explain the three cases:
      - leaf: just remove it
      - one child: replace the node with its child
      - two children: replace with the in-order successor (smallest in the
        right subtree), then delete that successor
    Knowing the algorithm without having coded it is a fine answer. Bluffing
    that it exists is not.

IF YOU GET STUCK

  this is a tree search, not a scan" is most of the mark.

6. QUESTIONS SPECIFIC TO THIS MODULE
--------------------------------------------------------------------------------

Q: What is the worst case for your BST?    *** ALMOST CERTAIN TO BE ASKED ***
A: "If confirmation numbers arrive in already-sorted order, every insert goes
   right and the tree degenerates into a linked chain. Search becomes O(n) -
   no better than a list, but with the memory overhead of nodes. Our
   confirmation numbers are effectively random 8-digit values, so the tree
   stays roughly balanced in practice. The proper fix is a self-balancing tree,
   AVL or red-black, which rebalances on insertion. That was beyond this
   assignment's scope."
   Draw the degenerate chain if you have a whiteboard. It lands well.

Q: Why compareTo on a String rather than parsing to a number?
A: 8-digit confirmation numbers are fixed length, so lexicographic order and
   numeric order agree. Be ready to admit that if lengths varied, "9" would
   sort after "10" and the ordering would break.

Q: Why a BST and not a hash table?
A: A hash table would give O(1) average lookup, better than O(log n). But it
   gives no ordering - I would lose the free sorted output from the in-order
   traversal, and Menu 5 would need an actual sort. Also we cannot use Java's
   HashMap, so I would have had to build one.

Q: Your tree only holds Booking, not <T>. Why isn't it generic?
A: BE HONEST. "It is typed to Booking rather than generic. The team ADT that we
   submit for assessment is the List, which IS fully generic. If I rewrote the
   BST I would make it generic with a Comparator, the same way ArrayList.sort()
   takes one." The rubric's genericity criterion applies to the submitted team
   ADT - do not pretend the BST is something it is not.

Q: Which ADT method did YOU contribute to the team ADT?
A: See the action box at the top of this file. "I wrote the entire BST" is a
   strong answer but may not be what they are asking.

Q: Where does the non-linear ADT requirement get met for your team?
A: Here. You are it. Own that in your opening.

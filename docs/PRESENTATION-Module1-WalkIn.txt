--------------------------------------------------------------------------------
1. THE 60-SECOND OPENING
--------------------------------------------------------------------------------

"This module handles guests who arrive without a reservation. They are served
first come, first served, held in the team List ADT in arrival order.

A front-desk officer can flag a guest as URGENT for an operational exception -
an elderly or unwell guest, a wheelchair user, a guest with an infant, a
medical situation, or a complaint escalation. The reason is recorded so the
override can be audited afterwards.

To be clear about scope: urgent here is a desk decision, not loyalty-tier
priority. Tier-based allocation is a different module and this one deliberately
does not touch it.

I use two ADTs. The List holds the register - it is what lets me search,
filter, sort and page through the same data for the reports. The Stack backs
the undo feature, because undo is last-in-first-out by definition."

3. ADT WALKTHROUGH - LIST
--------------------------------------------------------------------------------

DECLARATION                             line 50
    private ListInterface<WalkInGuest> walkInRecords;

  Declared by INTERFACE, not by ArrayList. Spec §4.5.4 asks about exactly this.
  If asked: it restricts callers to the interface methods, and the
  implementation class could be swapped without changing any other line here.


STEP 1 - REGISTER                       registerWalkIn(), line 186

  Normal guest joins the back:
      walkInRecords.add(guest);                     O(1) amortised

  Urgent guest is INSERTED, not appended:
      int pos = findUrgentInsertPosition();
      walkInRecords.add(pos, guest);                O(n) - shifts the rest right

  findUrgentInsertPosition()            line 233
      Returns the position AFTER the last waiting urgent guest and BEFORE the
      first waiting normal guest.

      Queue:  [U1] [U2] [N1] [N2] [N3]
      New urgent guest goes at position 3:
              [U1] [U2] [U3] [N1] [N2] [N3]

      So an exception jumps the normal queue but NEVER overtakes an earlier
      exception. This prevents starvation and is more defensible than always
      inserting at position 1.

      SAY THIS: "Always inserting at the front would let a late urgent guest
      overtake one who has already been waiting. That is unfair and it is a
      starvation risk, so I insert behind the existing urgent guests."


STEP 2 - AUTO-ASSIGNED GUEST ID         generateNextGuestId(), line 156

  Scans all existing records for the highest WG#### and adds one.

  SAY THIS: "I scan instead of keeping a counter deliberately. If the counter
  said 53 and an undo freed WG0053, the next registration would collide.
  Scanning is O(n) but always correct."

  This is a good answer to "why is this not just a variable?"


STEP 3 - DISPLAY THE QUEUE              displayQueue(), line 351

      ListInterface<WalkInGuest> waiting = walkInRecords.filter(isWaiting());

  filter() walks all n entries, tests each with the Condition, and returns a
  BRAND NEW list. The master list is untouched.

  The Conditions are at lines 74-103:
      isWaiting()             status is WAITING
      hasStatus(String)       parameterised status test
      isUrgent(boolean)       urgent or normal
      arrivedOn(LocalDate)    arrived on a given date
      both(c1, c2)            AND-combines two conditions

  SAY THIS about both(): "This is how I do multi-criteria filtering without
  adding another operation to the ADT - I compose two Conditions into one."
  The spec asks reports to apply filters on multiple criteria; this is how.


STEP 4 - SEARCH                         searchByGuestId(), line 421

      walkInRecords.search(g -> g.getGuestId().equalsIgnoreCase(id));

  search() returns the FIRST match, or null. Linear, O(n).
  Guest IDs are unique, so first match is the only match.

  searchByName() (line 453) uses filter() instead, because a partial name can
  match many guests. Knowing WHY the two differ is a likely question.


STEP 5 - SORTED LISTINGS                displaySorted(), line 527

      ListInterface<WalkInGuest> copy = walkInRecords.filter(guest -> true);
      copy.sort(comparator);

  filter(guest -> true) copies the whole list. THE COPY IS SORTED, NEVER THE
  MASTER.

  SAY THIS: "Viewing a sorted listing must not reorder the actual queue.
  Someone browsing an A-Z listing should not change who gets served next. So I
  sort a copy every time."

  This is the single best design decision in the module to highlight. Demo step
  8 above proves it on screen.

  The four Comparators are at lines 105-155:
      byArrivalTime()             chronological
      byName()                    A-Z
      byWaitingTimeDescending()   longest wait first
      byServiceOrder()            urgent first, then arrival within each group


STEP 6 - THE MERGE SORT ITSELF          ArrayList.sort()

  Split the array in half, recursively sort each half, merge back by repeatedly
  taking the smaller front element. When two entries compare EQUAL, the merge
  takes from the LEFT half first - that is what makes it STABLE.

  WHY STABILITY MATTERS HERE - have this example ready:
      Sorting by NAME, two guests both called "Lim":
          Lim arrived 09:00, Lim arrived 10:30
      A stable sort keeps them in that order. An unstable sort might swap them,
      and the desk would serve the later arrival first for no visible reason.

  O(n log n) in ALL cases - best, average and worst. Unlike bubble or selection
  sort which are O(n^2). Trade-off: merge sort needs O(n) extra space for the
  merge; the exchange sorts sort in place.

  Collections.sort() is NOT used anywhere. Only Comparator, which §1.1.4 allows.


STEP 7 - REPORTS                        lines 577 and 727

  Report 1 - Queue Performance Analysis          generateQueuePerformanceReport()
      filter(arrivedOn(today))     narrow to today
      countIf(...)                 served / waiting / cancelled tallies
      sort(byWaitingTimeDescending())  top 3 longest waits
      displayHourlyChart()         arrivals-per-hour ASCII bar chart, peak hour

  Report 2 - Urgency Exception Audit             generateUrgencyAuditReport()
      filter(isUrgent(true)) and filter(isUrgent(false))
      averageWaitOf() on each      measured impact of the override
      displayReasonChart()         which reasons were used, charted

  BOTH combine searching + sorting + multi-criteria filtering, which is exactly
  what the spec demands. Neither one just lists entries - §4.5.3 says listing
  everything does not count as a report.

  SAY THIS if asked what makes it a report and not a listing: "Report 2 does
  not just show urgent guests. It compares their average wait against normal
  guests, so it answers whether the override actually achieves anything. That
  is a management decision-support question."

4. ADT WALKTHROUGH - STACK
--------------------------------------------------------------------------------

DECLARATION                             line 57
    private StackInterface<WalkInGuest> registrationHistory = new ArrayStack<>();

WHY A STACK
  Undo is LIFO by definition - you always reverse the most recent action.
  Nothing here needs to reach into the middle of the history, so the restricted
  interface is a feature: an out-of-order undo is impossible to write.


STEP 1 - EVERY REGISTRATION PUSHES      line 215
    registrationHistory.push(guest);

  After registering Ali, Siti, Kumar:
            top -> [ Kumar ]
                   [ Siti  ]
                   [ Ali   ]  <- bottom


STEP 2 - UNDO                           undoLastRegistration(), line 251

    WalkInGuest lastRegistered = registrationHistory.peek();   // LOOK first
    ...display exactly which registration will be removed...
    if (userConfirmsYes) {
        registrationHistory.pop();                             // then COMMIT
        walkInRecords.removeEntry(lastRegistered);
    }

  peek() reads the top WITHOUT removing it, so the user can be shown what they
  are about to lose. pop() only runs after Y.

  If the user answers N, the stack is untouched - Kumar is still on top and a
  later undo still finds him.

*** THE BUG THIS FIXED - YOUR BEST TALKING POINT ***

  The first version called pop() BEFORE asking the question. Answering "No"
  still discarded the record from the stack, so the next undo silently skipped
  one guest.

  SAY THIS: "Adding the confirmation prompt exposed a real bug. I was popping
  before asking, so declining still consumed the history. peek-then-pop is the
  correct pattern for any confirm-before-destroy operation."

  Tutors reward knowing WHY your code is shaped the way it is. This is a
  concrete, honest example - use it.


STEP 3 - NOT PERSISTED - ON PURPOSE

  The stack is never written to disk. An undo only makes sense for actions
  taken in the current run; offering to undo yesterday's registration would be
  wrong. If asked "why is the Stack not saved?", that is the answer.

5. LIVE CODING - LIKELY REQUESTS AND HOW TO ANSWER
--------------------------------------------------------------------------------

RULE: reach for an ADT operation first. Most requests are one call plus a
Condition or a Comparator. Do not hand-roll a loop, and never touch java.util.

"Add a filter for guests who waited more than 30 minutes."
    ListInterface<WalkInGuest> longWaits =
        walkInRecords.filter(g -> g.getWaitingMinutes() > 30);
  One filter() plus a lambda Condition. Follow the pattern at line 461.

"Count how many urgent guests there are."
    int n = walkInRecords.countIf(isUrgent(true));
  countIf() already exists. Do not write a loop.

"Sort by contact number."
    Add a Comparator next to the ones at line 105:
        private Comparator<WalkInGuest> byContact() {
            return (a, b) -> a.getContactNumber().compareTo(b.getContactNumber());
        }
    then  displaySorted(byContact(), "BY CONTACT NUMBER");
  displaySorted() already handles the copy, the sort and the pagination.

"Find the guest at position 5."
    walkInRecords.getEntry(5);
  Remember: 1-BASED. Position 5 is the fifth guest, not the sixth.

"Combine two filters - urgent AND waiting."
    walkInRecords.filter(both(isUrgent(true), isWaiting()));
  both() at line 96 exists exactly for this.

"Remove a specific guest."
    walkInRecords.removeEntry(guest);       by object
    walkInRecords.remove(position);         by 1-based position

IF YOU GET STUCK
  Say what you would do and why, then write it. Reasoning aloud scores better
  than silence. "I need a new list of matching entries without touching the
  master, so this is a filter with a Condition" is most of the mark.

6. QUESTIONS SPECIFIC TO THIS MODULE
--------------------------------------------------------------------------------

Q: The waiting line is a queue. Why is it a List and not your Queue ADT?
A: THIS IS THE MOST LIKELY HARD QUESTION. Answer:
   "Conceptually it is a queue, and FIFO is enforced in the control logic. But
   a Queue ADT only exposes the front. This module has to search by ID, filter
   by status, sort four different ways and paginate - none of which a Queue
   interface can do. Using a Queue would have meant copying data out of it
   constantly. The List gives me positional access and full traversal, so it
   was the honest choice. It is a deliberate trade-off, not an oversight."

Q: Why is inserting an urgent guest O(n)?
A: add(position, entry) shifts every later element right by one. Acceptable
   because urgent registrations are rare exceptions, and the queue is small.

Q: What if two guests arrive at the same time?
A: The List preserves insertion order, and the merge sort is stable, so they
   stay in the order they were registered. Ties never reorder unpredictably.

Q: How does pagination know the "Ahead" count across pages?
A: The counter is computed from the guest's position in the full filtered list,
   not from the row index on the page, so it continues correctly instead of
   restarting at each page boundary. Served and cancelled guests show "-".

Q: Why 52 sample records?
A: So pagination is demonstrable on a fresh run - 3 pages at 20 rows, with 23
   still waiting, 25 served and 4 cancelled.

Q: Your validation - is it required?
A: §4.5.1 requires only validations that invoke a collection ADT method. The
   name and contact validation goes beyond that. Say so honestly: "the input
   validation is extra; the ADT-level validation is the duplicate-ID check via
   the collection."

6b. TESTING DONE, AND WHAT IT FIXED
--------------------------------------------------------------------------------

HOW THE MODULE WAS TESTED

  The module was driven end to end with scripted input over every submodule -
  all registration paths, the undo in each of its states, serving, cancelling,
  every search and filter, all four sorted listings, both reports, and the
  pagination controls. Every validation branch was entered deliberately with
  bad input to check it produces its own specific message rather than one
  generic "invalid".

  Alongside that, 87 assertions were written against the registration logic -
  guest ID generation, the urgent insertion policy, the undo stack, both
  validation rules, and the List ADT operations registration uses. All passed.
  Those checks were themselves verified by deliberately breaking the urgent
  insertion policy so an urgent guest always jumped to the front: exactly the
  four assertions guarding the starvation rule failed, which proved they were
  testing the rule rather than passing regardless.

  That test file has been REMOVED from the project. The specification does not
  ask for tests anywhere - they are absent from the deliverables (page 5), the
  report template (page 8, which is Part A plus control classes and
  screenshots), and the three assessment criteria (page 4). It earned no marks
  and had no place in the report, so it is not part of the submission.

  IF ASKED "how do you know your code works?" - describe what is in this
  section. The testing was done and it found the four defects listed below;
  the throwaway harness used to do it is simply not a deliverable.

FIXES FOUND BY THAT TESTING

  1. QUITTING A PAGED LISTING TOOK TWO KEYSTROKES AND LEFT THE TABLE ON SCREEN
     Pressing [Q] to leave a listing then showed "Press Enter to continue..."
     with the whole table still displayed. Two stops to leave one screen.

     FIXED: displayGuestList() now returns true when the user quits a paged
     listing and clears the screen on the way out. The menu loops call
     pauseUnlessQuit(), which skips the redundant pause. Single-page listings
     still pause, because they have no [Q] prompt and would otherwise vanish
     before being read.

     SAY THIS if asked about the design: "[Q] is already the user saying they
     have finished looking. Asking them to press Enter again to confirm they
     have finished is a stop that carries no information."

  2. SERVE NEXT GUEST HAD NO CONFIRMATION
     One keystroke permanently marked a guest SERVED, while Cancel and Undo
     both confirmed first. Inconsistent, and irreversible from inside the
     module.

     FIXED: it now shows who is at the front of the queue and asks Y/N.
     Answering N leaves them waiting. All three state-changing actions -
     serve, cancel, undo - now follow the same show-then-confirm pattern.

  3. FILTER CANCEL WAS SILENT
     Entering 0 at "Filter by status" or "Filter by guest type" returned with
     no message, so it was not obvious anything had happened. Search by name
     already said "Search cancelled." FIXED: both now say "Filter cancelled."

  4. REGEX REPLACED WITH HAND-WRITTEN CHARACTER CHECKS
     Validation used String.matches() and replaceAll(). Those are String
     methods, NOT collection classes, so they were never a rule violation -
     but a regex hides the rule inside a pattern string.

     FIXED: replaced with isLetter(), isDigit(), containsLetter(),
     hasOnlyNameCharacters(), hasOnlyContactCharacters(), digitsOf() and
     isAllDigits() - plain loops in WalkInRegistrationBookingUI. Behaviour is
     identical; every validation branch was re-tested afterwards.

     IF ASKED "why not use a regex?": "The loop states the rule directly in
     Java and can be stepped through a character at a time. A regex is a
     second language hidden in a string - it works, but you cannot show the
     marker what it does without decoding it first."

  5. STALE SEEDED ARRIVAL TIMES
     walkInGuests.dat still held data seeded on 10 August, so guests showed
     waits like "347h 30m". The initializer was correct - it seeds relative to
     now - the .dat file was just old. FIXED by deleting it so it regenerates.

     DO THIS AGAIN before taking your report screenshots: delete
     walkInGuests.dat, run once, then capture. Otherwise your screenshots will
     show absurd waiting times.

VERIFIED WORKING - things the testing confirmed are already correct
  - Cancel at the FIRST input of registration (entering 0 as the name) aborts
    cleanly. Cancel also works at the contact and urgency-reason prompts.
  - Undo answering N leaves the stack AND the records untouched, and the next
    undo still finds the same guest. The peek-then-pop fix holds.
  - Cancel-a-guest answering N leaves the guest WAITING; answering Y cancels.
    Both name the specific guest before asking.
  - Every name and contact validation branch fires its own specific message.
  - Invalid menu input - letters, out-of-range, negatives, decimals, empty -
    all re-prompt with a clear message rather than crashing.
  - Every submodule and both reports ran end-to-end with no exceptions.

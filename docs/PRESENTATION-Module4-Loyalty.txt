1. THE 60-SECOND OPENING
--------------------------------------------------------------------------------

"This module runs the membership programme. Members earn points, move up tiers,
redeem rewards, and get notified when something changes or their points are
about to expire.

I use two ADTs. The team's List holds members, rewards, redemption history and
notifications - four separate collections. And I use a Queue for pending
redemption requests, because redemptions must be processed in the order they
were requested. A member who asked first gets served first.

The Queue is the interesting choice. I could have used a List and just always
taken the first element, but then nothing stops someone processing out of
order. The Queue has no operation that reaches past the front, so fairness is
enforced by the structure rather than by me remembering to be careful."

3. ADT WALKTHROUGH - QUEUE      *** YOUR HEADLINE ADT ***
--------------------------------------------------------------------------------

DECLARATION                             line 66
    private QueueInterface<Redemption> pendingRedemptionQueue = new ArrayQueue<>();

  Declared by INTERFACE. Spec §4.5.4 asks about exactly this.

WHY A QUEUE
  Redemption requests must be processed in arrival order. FIFO IS the fairness
  rule. Because the interface exposes only the front, jumping the queue is not
  something I chose to prevent - it is impossible to express.


STEP 1 - REQUEST                        requestRewardRedemption(), line 328
    pendingRedemptionQueue.enqueue(redemption);          // line 371

  After Ali, then Siti, then Kumar request rewards:

      front -> [ Ali ] [ Siti ] [ Kumar ] <- back
      getNumberOfEntries() = 3

  Nothing is sorted. Nothing is compared. Arrival order IS the order.


STEP 2 - PROCESS                        processNextPendingRedemption(), line 388

    if (pendingRedemptionQueue.isEmpty()) { ...nothing pending... }   // line 389
    Redemption redemption = pendingRedemptionQueue.dequeue();         // line 394

  Ali comes out.

      front -> [ Siti ] [ Kumar ] <- back
      getNumberOfEntries() = 2


STEP 3 - THE CIRCULAR ARRAY - KNOW THIS

  ArrayQueue is a CIRCULAR array. dequeue() moves the front INDEX forward and
  wraps around with modulo. It does NOT shift the elements.

      Before dequeue:  front=0  [Ali ][Siti][Kumar][    ][    ]
      After  dequeue:  front=1  [    ][Siti][Kumar][    ][    ]

  SAY THIS: "That is why dequeue is O(1). A naive array queue would shift every
  element left on each removal, making it O(n). The circular index avoids all
  of that - and when the back reaches the end of the array it wraps into the
  space the front has vacated, so no capacity is wasted."

  THE POINT TO MAKE ON STAGE:
  "Notice I never told the system who was first. The Queue ADT has no operation
  that can reach past the front, so processing out of order is not something I
  chose to prevent - it is something the ADT makes impossible."

  LIKELY FOLLOW-UP: "Why not a List and always take position 1?"
  ANSWER: "Functionally identical, but a List exposes getEntry(3). Someone
  maintaining this later could process Kumar first without anything stopping
  them. The Queue removes that possibility at compile time. Choosing the
  restricted ADT is a correctness guarantee, not a limitation."

7. QUESTIONS SPECIFIC TO THIS MODULE
--------------------------------------------------------------------------------

Q: Why doesn't your module save to a file?
A: BE HONEST - this is the most likely awkward question. Modules 1, 2 and 3 all
   persist to .dat files; you do not.
   ANSWER: "My data is rebuilt in memory on every run from RewardInitializer.
   For a prototype demo that is a deliberate choice - every run starts from a
   known state, so the demo is repeatable and there is no stale-file problem.
   The spec explicitly allows populating collections with hard-coded entity
   values (§B.1). If this were production I would add a DAO like the other
   modules - it is the same pattern, my module just does not have one yet."
   Do not pretend it persists. Own it as a prototype choice with a spec citation.

Q: Your queue is not persisted either - what happens to pending redemptions?
A: They are lost on exit. Same answer as above. If pressed, the honest position
   is that a production system would serialise the queue too.

Q: Which ADT method did YOU contribute to the team ADT?
A: You are the second-heaviest USER of the added operations, but git shows all
   six were authored in one commit by Tan Chee Yan. See
   docs/PRESENTATION-General.txt section 2 for the team plan. Suggested
   addition that fits your module:
       groupCount(Condition) or a sum operation on the List
       - your tier and redemption reports tally by category with hand-written
         loops. One ADT operation would replace several of them.
   Author it in BOTH ListInterface.java and ArrayList.java, put your @author
   line on it, and call it from your reports.

Q: Why a Queue for redemptions but a List for everything else?
A: Different access patterns. Redemptions are processed strictly in order and
   only from the front - that is a Queue. Members and rewards need lookup by
   ID, filtering, sorting and full traversal - that is a List. Matching the ADT
   to the access pattern is the whole point of the exercise.

Q: The spec mentions a VIP tier module that keeps the highest tier at the
   front. Is that you?
A: NO - and know this. That is a separate module in the spec's table ("VIP &
   Loyalty Tier Priority Room Allocation") which your team did not build. It
   describes a heap or priority queue. Yours is a plain FIFO queue for
   redemption requests, and tier affects rewards and promotions, not room
   allocation order. Be clear on the distinction if asked.

Q: Your control class is 1609 lines. Is that well designed?
A: Fair question, answer honestly: "It covers thirteen use cases plus two
   reports, so it is large. The report row and summary classes are nested
   inside it - in a larger system I would split those out. The ADT usage and
   the business logic are cleanly separated, but the file itself could be
   decomposed further."

Q: Is your List declared by interface or by class?
A: Interface - all four of them. Spec §4.5.4. Know why.

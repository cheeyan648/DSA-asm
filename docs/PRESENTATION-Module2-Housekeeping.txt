1. THE 60-SECOND OPENING
--------------------------------------------------------------------------------

"This module records room cleaning work as an append-only log. Every status
update is a new entry - task ID, room number, status, timestamp - and a room's
current state is whatever its latest entry says. Nothing is ever edited in
place, so the log is a full audit trail of who changed what and when.

Statuses move Dirty, Cleaning In Progress, Inspected, Ready for Check-In.

I use two ADTs. The List holds the log in chronological order. The Stack backs
the rollback feature, because undoing a mistaken status update is last-in-
first-out by definition - you reverse the most recent one."

3. ADT WALKTHROUGH - LIST
--------------------------------------------------------------------------------

DECLARATION                             line 45
    private ListInterface<HousekeepingTask> taskLog;

  Declared by INTERFACE, not by ArrayList. Spec §4.5.4 asks about exactly this.
  If asked: it restricts callers to the interface methods, and the
  implementation class could be swapped without changing any other line.


STEP 1 - APPEND-ONLY LOGGING            line 172 area
    taskLog.add(newTask);
    statusHistory.push(newTask);

  Every update appends. Nothing is edited in place.

  SAY THIS: "I chose append-only because housekeeping needs an audit trail. If
  I overwrote the status, I would lose the history of who changed what and
  when, and the rollback would have nothing to roll back to."


STEP 2 - THE CURRENT-STATE COLLAPSE     buildCurrentRoomList(), line 383

  THIS IS THE MOST INTERESTING PART OF YOUR MODULE. Lead with it.

  Problem: the log has many entries per room, but a status report needs ONE
  current row per room.

      Log:  Room 101  Dirty          08:00
            Room 102  Dirty          08:05
            Room 101  In Progress    09:15
            Room 101  Inspected      10:40      <- 101's current state
            Room 102  In Progress    09:30      <- 102's current state

      Collapsed:  Room 101  Inspected
                  Room 102  In Progress

  The method walks the log and keeps each room's LATEST entry, building a new
  List of current states.

  SAY THIS: "This is what makes an append-only history usable as a live status
  view. The log is the source of truth; the room list is a derived view built
  fresh each time, so it can never drift out of sync with the log."

  (If you add lastIndexOf() as suggested above, this method becomes the place
  you call it - and this is then also your ADT-contribution answer.)


STEP 3 - COUNTING UNIQUE ROOMS          countUniqueRooms(), line 672

    ListInterface<String> uniqueRooms = new ArrayList<>();
    ...for each task, if (!uniqueRooms.contains(room)) uniqueRooms.add(room);

  Uses a second List plus contains() to avoid double-counting.

  LIKELY QUESTION: "Isn't that O(n squared)?"
  HONEST ANSWER: "Yes - contains() is O(n) and it runs once per entry, so it is
  O(n squared) overall. With a few hundred log entries that is fine. If the log
  grew large I would want a Set ADT, but we are not allowed the Java one and a
  custom Set was outside my module's scope."

  Do not pretend it is efficient. Knowing the complexity and the trade-off
  scores better than claiming it is optimal.


STEP 4 - SORTING                        bubbleSortRoomList(), line 431
                                        bubbleSortActivityList(), line 642

  BUBBLE SORT with an early-exit swapped flag:

      for i = 1 to n-1
          swapped = false
          for j = 1 to n-i
              compare roomList.getEntry(j) with getEntry(j+1)
              if out of order:
                  roomList.replace(j, second);
                  roomList.replace(j+1, first);      <- swap via replace()
                  swapped = true
          if (!swapped) break;                       <- already sorted, stop

  Note it swaps using the ADT's replace() operation, not by touching an array.
  That is correct - the control class must go through the ADT interface.

  COMPLEXITY - know these:
      Worst / average   O(n squared)
      BEST              O(n)  when already sorted, thanks to the swapped flag
      Space             O(1)  sorts in place

  SAY THIS: "The early-exit flag matters here specifically. My log is already
  in chronological order, so sorting by time is the best case and finishes in a
  single pass. Without the flag it would always do the full n squared."

  IF ASKED "why not merge sort like Module 1?"
  "Merge sort is O(n log n) always, but it needs O(n) extra space. My lists are
  small and often already sorted, which is bubble sort's best case. Different
  data, different trade-off." That is a real answer, not an excuse.


STEP 5 - SEARCHING                      searchHousekeepingTask(), line 293

  LINEAR SEARCH over the log, by Task ID, Room Number, or Status.

      Task ID  -> breaks early on the first match (line 364), because task IDs
                  are unique so there cannot be a second one.
      Room     -> collects all matches, a room has many log entries.
      Status   -> collects all matches.

  SAY THIS: "The early break on Task ID is a small thing but it is deliberate -
  once a unique key matches, continuing to scan is wasted work."

  Complexity: O(n). Best case O(1) for a Task ID hit on the first entry.


STEP 6 - REPORTS                        line 475 and line 778

  Report 1 - Room Status Report
      buildCurrentRoomList()    collapse log to current state per room
      bubbleSortRoomList()      sort by room number, ascending or descending
      filtering by status       multi-criteria narrowing

  Report 2 - Housekeeping Activity Report
      filtered activity list    by status and/or date
      bubbleSortActivityList()  sort the result
      countUniqueRooms()        summary statistics

  BOTH combine searching + sorting + filtering, which is what the spec demands.
  Neither just lists the log - §4.5.3 says listing everything is not a report.

  SAY THIS if asked what makes it a report: "The Room Status Report does not
  show the log. It derives current state per room, which is information that
  does not exist as a row anywhere in the data - it has to be computed."

4. ADT WALKTHROUGH - STACK
--------------------------------------------------------------------------------

DECLARATION                             line 47
    private StackInterface<HousekeepingTask> statusHistory = new ArrayStack<>();

WHY A STACK
  The spec sentence for this module literally asks for instant rollback of the
  most recent status change. That is LIFO. Nothing needs to reach into the
  middle of the history, so the restricted interface is a feature: rolling back
  out of order is impossible to write by accident.


STEP 1 - EVERY LOGGED UPDATE PUSHES     line 172
    statusHistory.push(newTask);

  Also note line 37: existing tasks loaded from file are pushed at startup, so
  the history is populated from the seeded data too.

  After logging three updates:
            top -> [ Room 101 Inspected   ]
                   [ Room 102 In Progress ]
                   [ Room 101 In Progress ]  <- bottom


STEP 2 - ROLLBACK                       line 194 onward

    if (statusHistory.isEmpty()) { ...nothing to roll back... }

    HousekeepingTask lastTask = statusHistory.peek();      // LOOK first
    ...display exactly which update will be reversed...
    if (userConfirmsYes) {
        HousekeepingTask rolledBack = statusHistory.pop(); // then COMMIT
        ...remove it from the log...
    }

  peek() reads the top WITHOUT removing it, so the supervisor sees exactly what
  they are about to undo. pop() only runs after Y.

  SAY THIS: "peek-then-pop is the correct pattern for confirm-before-destroy.
  If I popped first and the user declined, the record would already be gone
  from the history and the next rollback would silently skip one."

  (Module 1 hit exactly that bug and fixed it the same way - the two modules
  share the pattern deliberately.)


STEP 3 - DUPLICATE STATUS REJECTION

  A task cannot be set to the status it already has.

  SAY THIS: "This prevents a meaningless entry entering the log - and more
  importantly it stops the rollback stack filling with no-op updates that would
  each need rolling back separately."

  Good answer to "what validation do you have?" Spec §4.5.1 wants validations
  that involve a collection operation, and this one reads the current state out
  of the List before deciding.

6. QUESTIONS SPECIFIC TO THIS MODULE
--------------------------------------------------------------------------------

Q: Which ADT method did YOU contribute?
A: See the action box at the top of this file. Have a real answer ready.

Q: Why append-only instead of updating the task in place?
A: Audit trail, and rollback needs a previous state to return to. Updating in
   place would destroy both.

Q: Your bubble sort is O(n squared). Why not something faster?
A: Answer honestly - see STEP 4. Small lists, often already sorted, sorts in
   place with no extra memory. Know that merge sort is the alternative and why
   you did not need it.

Q: What is the difference between your Stack and Module 1's?
A: Same ADT, same peek-then-pop pattern, different entity. Module 1 undoes a
   registration, you roll back a status update. Both are LIFO for the same
   reason.

Q: Why does the Stack get populated at startup (line 37)?
A: So a rollback works on seeded data too, not only on updates made in the
   current run. Be ready to say whether that is what you intended - if the
   tutor pushes, the honest position is that rollback of historical entries is
   a design choice, not an accident.

Q: What happens if you roll back twice?
A: The second pop returns the update before it. The stack keeps going until
   isEmpty(), then the module reports there is nothing to roll back. Demo it.

Q: Is your List declared by interface or by class?
A: Interface - ListInterface<HousekeepingTask>. Spec §4.5.4. Know why.

1. THE TEAM ADT IS  LIST
--------------------------------------------------------------------------------

  Specification + implementation submitted for Part A:

      src/adt/ListInterface.java      the Java interface
      src/adt/ArrayList.java          array implementation, generic <T>

  The spec (Part A) requires exactly ONE collection ADT to be submitted and
  assessed. That is the List. Every member must be able to show where they use
  it.

WHY LIST WAS CHOSEN AS THE TEAM ADT
  All four modules need the same three things: keep records in a known order,
  reach any record by position, and walk every record for reports. Only a list
  does all three. Stack, Queue and BST each expose one access pattern; the List
  is what every module could actually build on.

CORE OPERATIONS  (adapted from the course sample code by Frank M. Carrano -
acknowledged at the top of both files, as Coding Standard 4 requires)

      add(T)                    append to end
      add(int, T)               insert at position, shift right
      remove(int)               remove by position, shift left
      replace(int, T)           overwrite at position
      getEntry(int)             read at position
      contains(T)               membership test
      getNumberOfEntries()      size
      isEmpty() / isFull()      state
      clear()                   empty the list
      getIterator()             iterate without exposing positions

  Positions are 1-BASED. First entry is at position 1.

ADDED OPERATIONS  (the "additional/modified operations" the rubric rewards
under "Collection ADT implementation - originality", weight 1.5)

      getPosition(T)            1-based position of an entry, or -1
      removeEntry(T)            remove first matching entry
      sort(Comparator)          own merge sort, stable, O(n log n)
      filter(Condition)         new list of entries satisfying a condition
      search(Condition)         first entry satisfying a condition
      countIf(Condition)        how many entries satisfy a condition

  adt/Condition.java is a one-method interface written to support the last
  three. It lets the collection express "which entries" without knowing
  anything about the objects it holds, and avoids depending on a predefined
  Java functional interface.

3. RULES YOU MUST NOT BREAK  (from the spec Q&A - know these cold)
--------------------------------------------------------------------------------

  NO Java Collections Framework.  (§1.1.3)
      Banned: java.util.List, ArrayList, LinkedList, Set, HashSet, TreeSet,
      Map, HashMap, TreeMap, Stack, Vector, Queue, Deque, ArrayDeque,
      PriorityQueue, Dictionary, Arrays, and the functions/functional packages.

  Comparator - ALLOWED.  Collections.sort() - BANNED.  (§1.1.4)
      We use Comparator only, and our own merge sort inside ArrayList.sort().

  Non-collection Java classes - allowed.  (§1.1.5)
      String, Double, Character, LocalDate, LocalDateTime, DateTimeFormatter,
      ChronoUnit, Scanner - all fine.

  java.util.Iterator - allowed.  (§1.1.6)

  Entity classes must be POJOs.  (§4.2.2)
      No Scanner, no System.out.println in any entity class.

  Declare variables by INTERFACE, not implementation.  (§4.5.4)
      Write   ListInterface<Member> memberList = new ArrayList<>();
      Not     ArrayList<Member> memberList = new ArrayList<>();
      Reason: restricts callers to the interface methods, and lets the
      implementation class be swapped without changing any other code.
      Our code follows this everywhere - point it out if asked.

  Reports must NOT just list everything.  (§4.5.3)
      Listing all entries is already a separate use case. A report must combine
      searching + sorting + multi-criteria filtering. All eight of our reports
      do.

  Two reports minimum per member.  (spec, Reports generation)

5. QUESTIONS THE TUTOR IS LIKELY TO ASK - AND THE ANSWERS
--------------------------------------------------------------------------------

Q: Why did you choose this ADT for this feature?
A: Answer in terms of ACCESS PATTERN, not convenience.
     List  - need ordered records, access by position, full traversal.
     Stack - undo is LIFO by definition.
     Queue - fairness is FIFO by definition.
     BST   - frequent lookup by unique key, want O(log n) not O(n).

Q: Why not just use a List for everything?
A: You could, but the restricted ADT enforces the business rule. A Queue has no
   getEntry, so processing out of order is impossible to write by accident. The
   ADT choice is a correctness guarantee, not just storage.

Q: What is the time complexity of that operation?
     ArrayList  add to end O(1) amortised, add at position O(n),
                getEntry O(1), remove O(n), contains O(n),
                sort O(n log n), filter/search/countIf O(n)
     ArrayStack push/pop/peek O(1)
     ArrayQueue enqueue/dequeue/getFront O(1)  (circular array - no shifting)
     BookingBST add/search O(log n) average, O(n) worst case

Q: Why is your sort stable / why does stability matter?
A: When two entries compare equal, merge takes from the LEFT half first, so
   equal entries keep their original relative order. It matters because sorting
   by name must leave tied entries in their original arrival order.

Q: Show me where you use the team ADT.
A: Have the file open and the line ready. Know your ListInterface declaration
   line by heart.

Q: What happens when the array is full?
A: doubleArray() allocates a new array of twice the capacity and copies across.
   That is why add is O(1) AMORTISED, not O(1) worst case.

Q: What is the worst case for your BST? (Module 3)
A: If keys are inserted in already-sorted order every node goes right and the
   tree degenerates into a linked chain - search becomes O(n). Fix is a
   self-balancing tree (AVL, red-black), beyond this assignment's scope.

Q: Why is Condition.java there instead of java.util.function.Predicate?
A: Predicate is in the banned functional package (§1.1.3), and the ADT should
   be self-contained. Condition is our own one-method interface.

Q: Can you add a feature right now? (live coding)
A: Stay inside the ADT. Reach for filter/countIf/search/sort first - most
   requests are one call plus a Condition or Comparator. Do not hand-roll a
   loop if an ADT operation already does it, and never reach for java.util.

5b. COMPLIANCE AUDIT - DONE 2026-08-24, AND WHAT WAS FIXED
--------------------------------------------------------------------------------

The whole project was audited against the specification. Four real violations
were found and fixed. If the tutor asks whether you checked the rules, this is
your answer - and the first one is worth mentioning unprompted, because finding
it yourself reads well.

  1. BANNED COLLECTION CLASS IN THE BANNER      *** was a real violation ***
     utility/MessageUI.java held the block-letter alphabet in a
     java.util.HashMap<Character, String[]>. HashMap and Map are both named in
     the §1.1.3 ban list. It was hidden because it was written fully-qualified
     (java.util.HashMap) instead of imported, so it never appeared in an import
     list.

     FIXED: replaced with two parallel arrays (BANNER_KEYS and BANNER_GLYPHS)
     plus a findGlyph() linear scan. Plain arrays are not collection classes,
     so this is compliant. Output is byte-for-byte identical.

     IF ASKED "why an array and not a map?":
     "The alphabet is 28 fixed entries that never change at runtime, so it does
     not need a dynamic structure. A linear scan is at most 28 comparisons per
     character drawn, which is nothing. And the assignment does not permit any
     Collections Framework class, so a map was never an option."

  2. CONTROL CLASSES WRITING TO THE CONSOLE     ECB violation
     The Coding Standards say control objects may communicate with boundary and
     entity objects - NOT with the actor. Three control classes called
     System.out directly: FrontDeskServiceMaintenance (5 headings),
     WalkInRegistrationBookingMaintenance (3), TARUMTResortUI (3).

     FIXED: routed through the boundary instead -
       FrontDeskServiceUI.displayScreenHeading(String)
       WalkInRegistrationBookingUI.displayBlankLine()
       WalkInRegistrationBookingUI.displayExceptionRow(WalkInGuest)
       MessageUI.displayBlankLine()
     No control class contains a System.out statement any more.

  3. TWO ENTITY CLASSES MISSING toString AND equals    §4.2.1
     BillingRecord and FrontDeskRecord had neither. The other seven entities
     had both.

     FIXED: added equals, hashCode and toString to both. BillingRecord compares
     on confirmation number; FrontDeskRecord compares on its booking and bill.
     This matters practically, not just for the rubric - the List ADT's
     contains(), getPosition() and removeEntry() all rely on equals().

  4. MISSING @author                            Coding Standard 3
     dao/RewardInitializer.java had none. FIXED.

ONE OPEN QUESTION - ASK YOUR TUTOR
  adt/Condition.java is annotated @FunctionalInterface, and we pass lambdas to
  filter/search/countIf. §1.1.3's ban list ends with "functions, functional".

  Our reading: that phrase refers to the java.util.function COLLECTION-related
  interfaces. @FunctionalInterface is in java.lang, not java.util, and it is
  only an annotation - it creates no collection and adds no behaviour. Condition
  itself is our own interface, written by us, precisely so we would not need
  java.util.function.Predicate.

  This is very likely fine. But it costs nothing to ask, and if your tutor
  reads the ban strictly the fix is trivial: delete the @FunctionalInterface
  line. Lambdas still compile against any single-method interface without it.
